## Where things live

- `frontend/src/app/core/transloco.providers.ts` - `provideTransloco`, `provideTranslocoLocale`, `provideTranslocoPersistLang`. This is the one place language config lives.
- `frontend/public/i18n/en-US.json` and `frontend/public/i18n/pt-BR.json` - translation strings. Angular 22's default static-assets directory is `public/`, not the legacy `src/assets/`; a custom `TranslocoLoader` (`frontend/src/app/core/transloco-loader.ts`) fetches from `/i18n/{lang}.json` to match.
- `frontend/transloco.config.js` - config for the `transloco-keys-manager` CLI (finds missing/orphaned keys; not used at runtime by the app itself).

## Rule: the backend never translates anything

The API returns machine-readable error codes, never translated strings:

```json
{ "error": { "code": "account.insufficient_balance", "params": { "available": "150.0000" } } }
```

`app/core/errors.py` (`AppError` + `app_error_handler`) enforces this shape.
The frontend maps `code` to a Transloco key itself (prefixing with `errors.`, say).
This keeps every translation in exactly one place.

## Rule: no hardcoded strings in templates

Every user-facing string goes through Transloco (`*transloco="let t"` + `t('some.key')`, or the `TranslocoDirective`/pipe). Run `task i18n:validate` (`transloco-keys-manager find`) before committing frontend changes - CI enforces this too, and it catches both missing keys (used in a template, absent from `pt-BR.json`) and orphaned ones (present in the file, no longer referenced).

One gotcha: the key-finder scans `.ts`/`.html` source text for calls matching
the configured marker (default `t`), including inside comments. A docstring
showing an example call like `` `t('foo.bar')` `` as literal text will register
as a false "missing key". Write example calls so they don't look like literal
invocations (see the comment in `frontend/src/app/core/api-error.ts` for the
pattern). Dynamic language-option keys use the same comment technique in the
shell templates.

## The language switcher exists on purpose

`frontend/src/app/layout/shell.ts` and the Settings screen expose both languages. Runtime language changes use `reRenderOnLangChange: true` and `transloco-persist-lang`; the active locale also updates the document language and date/number formatting.

The language preference is independent from display currency. New users start with English and USD, while an explicitly saved language or currency preference continues to win. Built-in demo records are data, not interface strings, and remain unchanged when the language changes.

## Layout: Some languages may be longer than English

Brazilian Portuguese strings are typically 20-30% longer than their English equivalents, and this can happen with another language too.
Don't build fixed-width buttons, don't truncate nav/table labels by default, and check any new layout at a narrow viewport (320px) before assuming it holds up.

## Currency formatting

`MoneyPipe` formats amounts using `TranslocoLocaleService`, which derives locale-appropriate grouping/decimal separators and the correct number of decimal digits per currency from `Intl.NumberFormat`, no hardcoded `2`.
See [`money-and-currency.md`](money-and-currency.md) for the more important rules around amount *precision* (this file is about *language*, that one's about *numbers*).
